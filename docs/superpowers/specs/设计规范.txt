我觉得这是一个非常好的时机。

实际上，很多独立游戏之所以 AI 越开发越像"后台管理系统"，就是因为只有 PRD，没有**设计系统（Design System）**。

你的这个项目我建议以后固定维护 **4 本核心文档**：

```
01 产品需求(PRD)
02 UI设计规范(UI Design)
03 UX交互规范(Game UX)
04 美术资源规范(Art Bible)
```

以后 Claude Code/Codex 每次开发之前，都先读取这四份文档。

这样后面开发几个月，整体风格都不会跑偏。

# 第一份：《古风手游 UI 设计规范（UI Design Specification）》

## 1、设计目标

### 设计理念

本游戏不是后台管理系统，不是网页应用，也不是传统 H5 页面。

整体设计目标：

> **让玩家始终感觉自己置身于真实宫廷，而不是操作一个系统。**

因此所有 UI 必须遵循：

**场景第一，UI第二。**

UI 永远只是漂浮在场景之上的信息层，而不是占据整个屏幕。

# 八、音效（新增）

建议增加一份 **Audio Bible（音频规范）**，这是很多 AI 项目容易忽略的部分，但对手游沉浸感影响极大。

包括：

* **环境音**：鸟鸣、风声、雨声、宫灯、脚步、朝堂人声、御花园流水等。
* **UI 音效**：按钮点击、卷轴展开、圣旨宣读、翻页、获得奖励。
* **人物语音**：妃嫔请安、大臣觐见、太监传旨等（后续可接入 TTS）。
* **背景音乐**：前朝、后宫、夜晚、朝会、祭祀、战争等主题 BGM。

## 我建议再增加一个文档（这是整个项目最重要的）

如果前面三份是"规范"，那最后还缺一个真正约束 AI 输出的文档：

> **《AI开发设计约束（AI Design Guardrails）》**

这个文档不描述功能，而是告诉 Claude Code、Codex 等 AI：

* 哪些 UI 绝对不能生成（后台风、白底卡片、现代按钮等）。
* 哪些交互绝对不能省略（重要操作必须有剧情、动画、反馈）。
* 哪些页面必须保持统一布局。
* 哪些资源必须优先复用而不是重新生成。

它相当于整个项目的"设计宪法"。有了它，后续几十万行 AI 生成代码，视觉和交互风格都会保持一致，而不会越开发越像一个普通 Web 系统。我建议把它作为整个项目的第五份核心文档，优先级甚至与 PRD 相同。
